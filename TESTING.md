# StylistApp Testing Guide

This project now has a layered automated test setup focused on the backend business logic and the main diploma user flows.

## Test Types

- Backend unit tests: auth, schemas, CRUD, storage, ML client.
- Backend integration tests: FastAPI endpoints under `/v1`.
- Security and ownership tests: user-scoped items, drafts, outfits, and body profiles.
- Storage tests: local filesystem and SeaweedFS HTTP behavior with mocked `requests`.
- ML client tests: `/segment` client behavior with mocked `requests.post`.
- Image-processing contract tests: `/segment` endpoint and YOLO class mapping without loading YOLO.
- Android unit tests: pure Kotlin DTO/formatter logic that can run without a device.
- Load tests: k6 scenario for login, items, outfits, profile, and optional outfit creation.

## Backend Tests

Backend package: `server-module/backend/app`.

Install test dependencies:

```bash
cd server-module/backend
pip install -r requirements.txt -r requirements-test.txt
```

Run all backend tests:

```bash
pytest
```

Run backend coverage with the required threshold:

```bash
pytest --cov=app --cov-report=term-missing --cov-report=html --cov-fail-under=80
```

When the Docker stack is already running, the same command can be executed inside the API container:

```bash
docker exec -w /app stylist_api pytest --cov=app --cov-report=term-missing --cov-report=html --cov-fail-under=80
```

HTML coverage report:

```text
server-module/backend/htmlcov/index.html
```

Current verified backend result:

```text

```

## Backend Test Database

The backend tests do not use the development PostgreSQL database.

`tests/conftest.py` sets `DATABASE_URL` to an isolated SQLite file in a temporary directory before importing the application package. Each test recreates the schema and gets clean data. PostgreSQL-specific JSONB columns are mapped through a portable SQLAlchemy JSON type for SQLite tests while still using JSONB on PostgreSQL.

## What Is Mocked

- SeaweedFS: no real SeaweedFS service is used in unit tests. SeaweedFS PUT/GET/HEAD calls are mocked.
- ML service: backend tests monkeypatch `segment_image_via_ml_service`.
- YOLO model: image-processing tests stub heavy dependencies and monkeypatch `process_uploaded_image_bytes`.
- External HTTP calls: `requests.post`, `requests.put`, `requests.get`, and `requests.head` are mocked where behavior matters.
- Android device services: Android tests are limited to pure JVM logic; device/location/weather integrations are not exercised in local unit tests.

These are mocked for speed, determinism, independence from external services, and to avoid loading the heavy YOLO model in ordinary test runs.

## Coverage Scope

Coverage target:

```text
backend line coverage >= 80%
```

No backend business files are hidden from coverage. The `.coveragerc` only configures reporting and standard pragma exclusions. Entry points, autogenerated files, migrations, and config-only files can be excluded later if such files are added and contain no business logic.

## Image-Processing Tests

Install dependencies:

```bash
cd image-processing-module
pip install -r requirements.txt -r requirements-test.txt
```

Run tests:

```bash
pytest
```

The tests cover:

- successful `/segment` contract;
- invalid content type;
- empty upload;
- model error response;
- response field contract;
- YOLO class to category mapping;
- missing model weights error.

## Android Unit Tests

Run local JVM tests:

```bash
cd "android app/app1"
./gradlew testDebugUnitTest
```

On Windows, if `java -version` points to Java 8, run Gradle with Android Studio JBR:

```powershell
$env:JAVA_HOME='C:\Program Files\Android\Android Studio\jbr'
$env:ANDROID_HOME="$env:LOCALAPPDATA\Android\Sdk"
$env:PATH="$env:JAVA_HOME\bin;$env:PATH"
.\gradlew.bat testDebugUnitTest
```

## Load Tests

Load tests are intentionally outside the pytest coverage pipeline.

Install k6, start the backend, then run:

```bash
k6 run load-tests/stylist-load-test.js
```

Useful environment variables:

```bash
BASE_URL=http://localhost:8000
EMAIL=load.user@example.com
PASSWORD=secret123
ITEM_IDS=item-id-1,item-id-2
```

The script measures:

- RPS through k6 summary metrics;
- average and p95 latency;
- error rate;
- 20 to 50 virtual users;
- login, `GET /v1/items`, `GET /v1/outfits`, `PUT /v1/profile/body`, and optional `POST /v1/outfits`.

Default thresholds:

```text
http_req_failed < 5%
p95 latency < 1200 ms
custom error rate < 5%
```
